# 1. 시공예정일 "확정 시점" 저장 ✅ 확정

사용자 요청: 예정일이 **언제 정해졌는지**를 데이터로 남긴다.

## 1.1 저장 방식 — 필드 값이 아니라 "사건"을 기록
현행처럼 날짜 값만 덮어쓰지 않고, **변경 이력(append-only)** 으로 쌓는다.

```
ScheduleEvent (append-only)
  taskId          (주방/욕실 각각 별도 Task)
  field           'scheduledAt' | 'timeSlot' | 'assignment'
  oldValue, newValue
  changedBy       (직원/영업자/기사)
  channel         office | tablet | mobile
  changedAt       ★ 이 시각이 "정해진 시점"
  reason          (시공연기 등일 때)
```

## 1.2 이걸로 계산되는 것
| 지표 | 정의 |
|---|---|
| **확정 리드타임** | 계약일 → 예정일이 처음 잡힌 `changedAt` |
| **재조정 횟수** | 같은 Task의 `scheduledAt` 변경 건수 (= 시공연기 빈도) |
| **주방/욕실 확정 간극** | 두 Task의 첫 확정 시각 차이 |
| **월별 확정 추이** | 예정일이 언제 몰려 잡히는가 |

> 주방·욕실이 별도 Task이므로 각각의 확정 시점이 따로 남는다.
> "예약은 예정일 2주 전까지 고객이 연락" 규칙의 실제 준수율도 측정 가능.

## 1.3 설계 결정 필요
- (a) **첫 확정 시점만** 필요한가, (b) **전 변경 이력**까지 필요한가?
  → 권장: **(b) 전체 이력**. 저장 비용 미미하고, 시공연기 분석에 그대로 쓰인다.
- 이 이력은 D5 감사로그와 통합 가능 (금액·상태·일정 변경을 한 테이블로).

# 2. 카카오 알림톡 ✅ 이미 하고 있고, 정식화하면 됨

## 2.1 현황
현행이 **이미 알림톡을 보내고 있다** (`/ajax/ajax_kakao_api.asp`):
- 기사배정 알림톡, 후기안내 알림톡 (계약관리 목록에서 일괄 발송)
- 친구톡 메뉴도 존재 (`/sub/10/kakao.asp`)

즉 발송 대행사·발신프로필이 **이미 세팅돼 있다.** 신규는 이걸 정식 모듈로 옮기는 일.

## 2.2 알림톡의 실제 제약 (알아둬야 할 것)
| 항목 | 내용 |
|---|---|
| 채널 | 카카오톡 채널(비즈니스) + 비즈니스 인증 필요 (이미 보유) |
| 대행사 | 카카오 비즈메시지는 **발송대행사** 경유 (예: NHN, 알리고, 인포뱅크, 비즈엠 등) — 검토 대상 |
| **템플릿 사전승인** | 문구를 미리 등록·심사받아야 함 (영업일 며칠 소요). 변수는 `#{이름}` 치환 |
| **정보성만** | 알림톡은 **거래 관련 정보성**만 가능 (계약확인·잔금안내·시공일정·완료). 홍보는 불가 |
| 홍보는 친구톡 | 박람회 홍보 등 마케팅은 **친구톡**(채널 친구 대상)으로 분리 |
| 대체발송 | 실패 시 SMS/LMS 자동 대체 (현행 SMS 인프라 재사용) |
| **버튼 지원** | 알림톡에 **웹링크 버튼** 삽입 가능 ★ → 3번 결제링크의 통로 |

## 2.3 신규 설계
```
NotificationTemplate  (알림톡/친구톡/SMS/메일 공통)
  channel, kakaoTemplateCode, body(변수), buttons[]
  category: 정보성 | 광고성
DeliveryLog  (발송·성공·실패·대체발송 이력)
Provider adapter  (대행사 교체 가능하게 추상화)
```
- 현행 SMS 상용구 → **알림톡 템플릿**으로 승격
- 잔금 안내·시공일 확정·완료 알림이 전부 **정보성**이라 알림톡으로 나감
- 자동화(잔금 회수 D-30/14/7 등)가 이 위에서 돈다

# 3. 카드 결제 링크 직접 발송 (결제선생 대체) ✅ 가능 — 단, PG는 필요

## 3.1 핵심 전제 ★
**우리가 카드사가 될 수는 없다.** 카드 승인·정산은 법적으로 **PG(전자결제대행)** 를 통해야 한다.
"결제선생" 같은 서비스도 실은 **PG 위에 얹은 UX 레이어**다.
→ 우리가 만드는 것은 "PG를 대체"가 아니라 **"결제선생이 하던 링크·발송·대사 UX를 우리 시스템 안에 직접 구현"** 하는 것. 이건 충분히 가능하다.

## 3.2 현행 구조 (이미 80% 비슷함)
현행도 사실상 링크 결제를 하고 있다:
- PG: **payjoa(페이조아)** — `api.payjoa.co.kr/pay/link`, CPID `CSL65111`
- 결제창에 `RESERVEDINDEX1 = SigongIdx` 를 참조로 넘김
- 결과는 `HOMEURL`(`pay_relocation.asp`) 리다이렉트로 수신
- **문제**: 결과가 리다이렉트라 놓치기 쉽고, 입금 레코드와의 **대사(매칭)가 수기**. 그래서 매출취소를 환불로 우회 입력하는 사태가 발생.

> ※ "결제선생"이 payjoa와 같은 것을 가리키는지, 별도 도구인지 확인 필요 (§4 Q).

## 3.3 신규 구조 — 결제선생이 필요 없어지는 이유
```
① 잔금 발생/시공완료
② 시스템이 결제링크 생성 (PG 결제 API 호출 → hosted checkout URL)
③ 알림톡 버튼으로 고객에게 발송  ← §2와 결합
④ 고객이 PG 보안페이지에서 카드 입력·결제 (카드정보는 우리가 안 만짐)
⑤ PG가 우리 시스템에 Webhook 통지 (승인/취소/실패)
⑥ Webhook → 원장에 PAYMENT 자동 기록  ← D1 원장과 결합
⑦ 자동 대사 완료 · 담당자 알림 · 영수증 발급
```
**결제선생 대비 이점**
- 발송·수납·대사가 **한 시스템에서 자동** (별도 도구·수기 대사 제거)
- 원장 직결 → 매출취소/환불 우회입력 문제 원천 소멸
- 알림톡 버튼과 결합 → **원클릭 잔금 결제**

## 3.4 PG 선택지 (검토 대상)
| 선택 | 특징 |
|---|---|
| **payjoa 유지** | 마이그레이션 리스크 최소. 결제 API는 그대로 두고 **링크·발송·대사·웹훅 레이어만 신규 구축** |
| **토스페이먼츠 전환** | 결제링크·API·웹훅 문서화가 강함, 개발 편의 우수 |
| 나이스페이 / KG이니시스 | 전통 PG, 안정적 |
| 부트페이 등 애그리게이터 | 여러 PG 통합, 초기 도입 빠름 |

→ **권장**: 1차는 **payjoa 유지 + 웹훅/대사 레이어 신설**(리스크 최소), 이후 필요 시 PG 교체. PG를 어댑터로 추상화해두면 갈아끼우기 쉽다.

## 3.4a PG 선정 기준 — 발송·승인조회·취소 3종 API ★

사용자 요구를 API 용어로 옮기면:
| 요구 | API | 이게 되면 |
|---|---|---|
| **발송** | 결제링크 생성 API | 잔금 링크를 시스템이 자동 생성 → 알림톡 버튼으로 발송 |
| **승인정보** | 결제 조회 API + **Webhook** | 승인번호·카드·금액·상태를 자동 수신 → 원장 자동 기록 |
| **취소요청** | 결제 취소 API (부분/전체) | ★ **외부 페이지 안 거치고 시스템에서 바로 취소** → 매출취소 자동 반영 |

> 현행의 가장 큰 통증(취소는 payjoa 외부페이지 → 매출취소 수기등록)이
> **취소 API 하나로 소멸**한다. 이 3종이 다 되는 PG를 고르는 게 핵심.

### 결제선생은 적합한가?
- 결제선생은 본질적으로 **가맹점용 UX 도구**다 — 대시보드/앱에서 **사람이 링크를 보내는** 방식.
- 우리 시스템에 **프로그램으로 임베드(붙이는)** 하는 개발자 API 플랫폼으로 설계된 것은 아니다.
- 파트너 API가 있을 수는 있으나, "우리 시스템이 자동 발송·조회·취소" 용도로는 **부적합할 가능성**. → 쓸 거면 API 범위를 직접 확인 필요(Q12).
- 결론: **임베드 목적이면 결제선생보다 개발자 우선 PG가 맞다.**

### 후보 비교
| 유형 | 서비스 | 발송(링크) | 승인조회 | 취소 API | Webhook | 특징 |
|---|---|---|---|---|---|---|
| **애그리게이터** | **포트원(PortOne, 구 아임포트)** | O | O | O | O | **하나의 API로 여러 PG** 연결. PG 교체해도 코드 안 바뀜. 락인 회피 |
| 애그리게이터 | 부트페이 | O | O | O | O | 유사 개념 |
| **단일 PG** | **토스페이먼츠** | O(결제링크) | O | O(부분취소) | O | **개발 문서·DX 최고** |
| 단일 PG | 나이스페이먼츠 | O | O | O | O | 전통 PG, 안정적 |
| 단일 PG | KG이니시스 | O | O | O | O | 최대 규모, 문서는 무거움 |
| 현행 | payjoa | 링크 O | △ | △(외부페이지) | 확인필요 | 유지 시 웹훅·취소API 지원범위 확인 필요 |

*표의 O/△는 일반적 포지셔닝 기준 추정. 최종 계약 전 각 사 API 스펙 실확인 필요.*

### 권장
1. **락인 회피·유연성 우선 → 포트원(애그리게이터)**
   - 한 API로 토스·나이스·이니시스·카카오페이 등 다PG. 나중에 갈아끼우기 자유.
   - 단, 애그리게이터 레이어 수수료/의존이 하나 더 낌.
2. **강력한 단일 PG로 단순하게 → 토스페이먼츠**
   - 문서·웹훅·취소API가 가장 깔끔. 우리처럼 직접 붙이는 데 최적.
3. **마이그레이션 리스크 최소 → payjoa 유지** (단 취소 API·웹훅 지원 확인이 전제)

> 어느 쪽이든 **PG를 어댑터로 추상화**해서 붙인다(§3.4). 그러면 1차는 A로 가고
> 나중에 B로 바꿔도 결제 로직 재작성이 없다. 애그리게이터를 쓰면 이 추상화가 사실상 내장.

### 취소 API의 주의점
- 취소는 **시점 규칙**이 있다: 정산 전(당일)은 승인취소, 정산 후는 환불(부분취소 가능여부 PG별 상이).
- **부분취소** 지원 여부·횟수 제한 PG마다 다름 → 계약 전 확인.
- 취소 성공 = Webhook 수신 → 원장에 `SALES_CANCEL`(매출취소) 또는 `REFUND`(환불) **자동 분개**. 둘 중 무엇으로 기록할지는 정산 시점으로 판별.

# 5. 세 기능의 결합점 (한 그림)

```
잔금 발생
  └→ [일정이력] 시공예정일 확정 → 회수 스케줄 기산점
  └→ [알림톡]   D-30/14/7 정보성 안내 + 결제버튼
  └→ [결제링크] PG 결제 → Webhook → [원장] 자동 입금기록
                                    → 대사 완료 → 완료 알림톡
```
→ 세 가지가 **잔금 회수 자동화(§05 PART3-C)** 하나로 수렴한다. 따로 만드는 기능이 아니라 한 파이프라인의 부품.
