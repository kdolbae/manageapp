1. 박람회비(170~520만)를 **선지출**
2. 계약금은 계약액의 **약 10%만** 수령 (50만 계약 → 5만)
3. 잔금 90%는 **입주 시점(수개월 후)** 회수

즉 **현금흐름이 구조적으로 마이너스**이고, 사업의 생사는 **잔금 회수율**에 달려 있다.
그런데 현행 시스템에는 잔금 독촉·회수 관리 기능이 **없다.** SMS 상용구에 잔금 안내문을 수기로 붙여 쓰고 있을 뿐이다.

> ➜ **신규 플랫폼의 1순위 가치는 "잔금 회수 자동화"다.** (PART 3 §C)

# PART 1. 진단 — 무엇을 고쳐야 하는가

## 1.1 기능은 충분하다. 구조가 문제다.
기능 100여 개는 이미 있다. 실패 지점은 전부 **구조**에서 나온다.

| 증상 | 실제 원인 |
|---|---|
| 매출취소를 입금 환불로 우회 입력 | 등록 UI가 태블릿에만 있고 **안내문 경로가 틀림** |
| 계약자 중복 등록 | 중복을 **보여주기만 하고 막지 않음** + 통합폼 실패 시 재시도 |
| 화면마다 다른 결과 | 같은 기능이 **PC/태블릿에 따로 구현** |
| 통계 숫자 불일치 | 집계식이 **화면마다 각각 하드코딩** |
| "22323번 건" 이 서로 다름 | 목록 번호가 **저장된 ID가 아닌 계산 순번** |
| 마진이 항상 마이너스 | 잔금 회수 기능 부재 (시스템이 아니라 **없는 기능**) |

## 1.2 신규 플랫폼이 반드시 지켜야 할 5원칙

| # | 원칙 | 현행 위반 사례 |
|---|---|---|
| P1 | **금액은 원장(ledger)에 기록한다.** 잔액은 저장하지 않고 원장 합계로 계산한다 | 매출취소·환불·입금이 별도 테이블에 흩어져 집계 불일치 |
| P2 | **다단계 저장은 하나의 트랜잭션이다** | 태블릿 4단계 체이닝, 중간 실패 시 고아 레코드 |
| P3 | **하나의 기능은 하나의 구현이다.** UI만 달라진다 | 접수형태 11종 vs 5종, `caltotal()` 두 버전 |
| P4 | **모든 개체는 불변 ID를 갖는다.** 표시번호는 별도 채번 | 목록 번호 = 역순 순번 |
| P5 | **화면은 데이터를 읽을 뿐 저장하지 않는다** | 입금 수정이 DOM 파싱, 계약서 메일이 DOM 스냅샷 |

# PART 2. 제안 아키텍처

## 2.1 무엇이 되는가 — 포지셔닝

현행은 **한 회사의 사내 시스템**이다. 요청하신 3가지(업체 소개 · 단가 공개 · 채팅)를 더하면 성격이 바뀐다.

```
            [현행 UFFICE]                    [신규 플랫폼]
         나노마스터 사내 도구       →     시공업체용 SaaS + 고객 접점
         지점 10개 = 같은 회사             업체 N개 = 서로 다른 사업자
         고객은 시스템을 못 봄             고객이 직접 들어와 보고 결제
```

**제안: 멀티테넌트 SaaS + 공개 마이크로사이트**

| 영역 | 사용자 | 내용 |
|---|---|---|
| **Public** | 일반 고객 | 업체 소개, 시공 사례, 단가표, 견적 요청, 후기 |
| **Customer** | 계약 고객 | 내 계약 조회, 잔금 결제, 일정 확인, 채팅, 후기 작성 |
| **Workspace** | 업체 직원 | 계약·시공·정산·경비·박람회 (현행 기능 전체) |
| **Field** | 시공기사 | 배정 확인, 사진 등록, 완료 보고, 정산 확인 |
| **Sales** | 영업자 | 박람회 일정, 현장 계약 작성, 비용 청구, 실적 |
| **Admin** | 플랫폼 운영 | 테넌트 관리, 요금제, 감사 |

> ⚠️ **확인 필요**: 업체 소개·단가 공개의 대상이
> (a) 일반 소비자 대상 **마켓플레이스**인지,
> (b) 각 업체가 자기 고객에게 쓰는 **브랜드 페이지**인지에 따라 설계가 달라진다.
> 본 문서는 **(b)를 기본**으로 하되 (a)로 확장 가능한 구조로 설계한다.

## 2.4 핵심 설계 결정 5가지

### D1. 금액은 원장(Ledger)으로 ★★★
현행의 근본 문제를 한 번에 해결한다.

```ts
// 저장하는 것: 사건(event)만
LedgerEntry {
  contractId, workOrderId?
  type: 'CONTRACT'|'DISCOUNT'|'VOUCHER'|'PAYMENT'|'REFUND'|'SALES_CANCEL'
  amountSupply  // 공급가
  amountVat     // 부가세
  occurredAt, method?, approvalNo?, memo, attachments[]
  createdBy, canceledBy?, canceledAt?   // 삭제하지 않고 취소 표시
}

// 계산하는 것: 잔액 (저장 안 함)
계약금액   = Σ CONTRACT
실계약금액 = Σ CONTRACT − Σ DISCOUNT − Σ VOUCHER − Σ SALES_CANCEL
입금액     = Σ PAYMENT − Σ REFUND
잔금       = 실계약금액 − 입금액
```

**효과**
- 매출취소와 환불이 **같은 원장의 다른 타입** → 우회 입력 불가능, 집계 자동 일치
- 모든 화면·통계가 **같은 함수**를 호출 → 숫자 불일치 소멸
- 원장은 **추가만(append-only)**, 수정은 반대 분개 → 감사 추적 완전

### D2. 상태 머신
```
Contract:  DRAFT → PENDING_APPROVAL → APPROVED → COMPLETED
                                    ↘ REJECTED  ↘ CANCELED
Task:      UNSCHEDULED → SCHEDULED → ASSIGNED → NOTIFIED
                       → IN_PROGRESS → DONE
                       ↘ POSTPONED  ↘ CANCELED
Expense:   DRAFT → CLAIMED → REVIEWED → APPROVED → PAID
                           ↘ REJECTED
```
전이 규칙을 코드 한 곳에 정의. 현행처럼 `예정`인데 기사가 비어 있는 모순 상태 방지.

### D3. 마스터 데이터는 전역, 사용은 테넌트별
현행은 아파트가 지점에 종속돼 같은 단지가 중복 생성된다.
```
Site (전역)  ─ 시도/시군구/단지명 unique
  └─ TenantSiteLink (테넌트별 별칭·메모·담당)
```
상품도 동일: `Product`(카탈로그) + `PriceRule`(테넌트·지점·기간별 단가).

### D4. 표시번호는 채번 테이블로
```
Contract { id: ULID (불변), displayNo: "2026-00123" (채번, 불변) }
```
목록 정렬이 바뀌어도, 신규 등록이 생겨도 번호가 변하지 않는다.

### D5. 알림·문서는 템플릿 엔진으로
현행은 계약서 메일이 **화면 DOM 스냅샷**이라 화면을 고치면 계약서가 깨진다.
```
DocumentTemplate (계약서·견적서·보증서·지급명세서)
  → 데이터 바인딩 → PDF 생성 (서버) → 저장 + 발송
NotificationTemplate (알림톡·SMS·메일) → 변수 치환 → 발송 → DeliveryLog
```

- 알림톡·SMS 템플릿 엔진
- 일정 관리 (캘린더·상한·휴무)

## Phase 3 — 대외 + 소통 (2~3개월)

- 온라인 견적 → 계약 → 결제

- 경비 결재 워크플로
- 박람회 손익 · 영업자 정산 · 지급명세서
- 대시보드 / BI
- Open API

## 마이그레이션 전략
| 단계 | 방법 |
|---|---|
| 1 | 현행 DB 스키마 추출 (ASP 뒤의 MSSQL 추정 — **확인 필요**) |
| 2 | 마스터 우선 이관 (계약자·아파트·상품·기사) + **중복 정리** |
| 3 | 계약·시공·입금 → 원장으로 **변환** (기존 환불↔매출취소 오분류 교정 포함) |
| 4 | 병행 운영: 신규 계약은 새 시스템, 기존 건은 조회 전용 |
| 5 | 잔여 건 종료 후 현행 종료 |

> ⚠️ 3단계가 핵심 난이도. 현행에서 **매출취소를 환불로 입력한 건**을 구분해야 하는데,
> 비고란의 `"M/D 취소"` 패턴과 결제내역의 `매출취소` 행을 대조하면 상당 부분 복원 가능하다.

# 부록 B. 계승할 업무 규칙 (놓치면 안 됨)

- 계약금액 = 시공금액 − 할인 − 상품권
- 시공비 3방식: 주방UV(기사단가+교통비) / 주방나노(공급가÷1.1×요율+교통비) / 상품별(Σ품목비+교통비)
- 접수형태 `옵션` → 첫 입금은 **중도금**으로 기록
- A/S 10년 / 해약은 시공 8일 전 / 잔금은 완료 고지 후 3일 이내
- 시공 순서: 베란다칠 → 줄눈 → 입주청소 → 새집증후군 ↔ 나노코팅
- 나노코팅과 입주청소·줄눈은 **같은 날 불가**
- 시공 예약은 예정일 **2주 전**까지 고객이 연락
- 일일 시공건수 상한 (지점·날짜별)
- 계약 전 확인사항 7종 (메탈 소재 제외, 포세린타일 약정 등) — 서명과 함께 보관
- 경비 결재 5단계, 개인지출(직원 선지출) 별도 추적
