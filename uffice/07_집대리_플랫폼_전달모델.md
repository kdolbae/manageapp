# 1. 무엇을 만드는가 (확정)

**집대리**: 입주 관련 **품목별 시공 협력업체**들이 함께 쓰는 계약관리 SaaS.

| 요구 | 설계 반영 |
|---|---|
| 협력업체용 멀티테넌트 | 나노마스터 = **테넌트 #1 + 플랫폼 운영자**. 각 협력업체 = 테넌트 |
| 모든 기능 포함, 업체별 on/off | **기능 권한(Entitlement)** 테이블로 UI·API 동시 게이팅 |
| 구독형 계정 개설 | 요금제(Plan) → 기능 매핑 + 구독 과금 |
| 별도 사업자로 독립 가능 (DB 합침/나눔) | **테넌트 격리** 설계: 기본 공유(RLS), 독립 시 전용 인스턴스로 분리 가능 |
| DB는 우리가 업로드 (직접접근 불가) | **Export → Import** 마이그레이션 (직접 연결 아님) |
| 오픈 최대한 빠르게, 개발자 없이 Claude+사용자 | **BaaS 기반 + MVP 우선** 전략 (아래) |

> 집대리는 박람회 모델과 정확히 맞물린다: 입주 박람회에서 코팅·줄눈·청소·절수페달 등
> **여러 협력업체가 한 현장에서 계약**한다. 집대리는 이들 모두의 계약을 관리하는 수평 플랫폼.

# 2. 현실 점검 — "개발자 없이 너와 나만" ★

이건 가능하다. 단, **역할을 명확히** 해야 한다. 결제·개인정보를 다루는 플랫폼이라 코딩만의 문제가 아니다.

## 2.1 역할 분담
| Claude(나)가 하는 것 | 사람(당신)이 **소유**해야 하는 것 |
|---|---|
| 아키텍처·DB 스키마 설계 | 사업자 등록 / **PG 가맹점 계약** |
| 코드 생성·화면·디버깅 | 도메인·호스팅·클라우드 **계정과 비용** |
| 마이그레이션 스크립트 | **시크릿·API 키 관리** (내가 대신 보관 못 함) |
| 문서·테스트·리뷰 | **개인정보 처리자 법적 책임** (개인정보보호법) |
| 기술 의사결정 근거 제시 | 운영 장애 시 **최종 판단·대응** |
| — | 약관·법무, 협력업체 영업·지원 |
| — | **데이터 정확성 최종 책임** |

→ 막는 요소가 아니라 **소유권 정리**다. 당신은 사실상 PM+운영자, 나는 코딩 엔진.

## 2.2 무엇이 이걸 가능하게 하나 — BaaS
개발자 없이 백엔드를 처음부터 짤 수 없다. 그래서 **Backend-as-a-Service**로 인프라를 산다:
- 인증·DB·파일저장·실시간·권한(RLS)을 **직접 안 만들고 관리형으로** 사용
- 우리는 **비즈니스 로직과 화면만** 만든다 → 백엔드 작업량 60% 감소

## 2.3 정직한 경고 (결정 전에 알아야 함)
- **결제·개인정보는 코딩이 아니라 책임의 문제.** 카드 처리는 PG로 offload하지만(§06),
  PG 가맹점 온보딩은 **사업자·심사로 수 주** 걸리고, 개인정보 22,000건은 법적 관리 대상이다.
- **남의 회사에 파는 순간** 당신은 SaaS 벤더가 된다: 협력업체 고객 데이터를 대신 처리 →
  **위탁계약**이 필요하고, 장애 시 **여러 업체가 동시에** 영향받는다.
- → 그래서 **"한 테넌트로 먼저 증명하고, 그다음 팔기"** 순서가 안전하다(§6).

# 3. 아키텍처 (무팀·고속 버전)

[05 §2.2]의 스택을 "개발자 없이 빠르게"에 맞게 조정:

| 층 | 선택 | 이유 |
|---|---|---|
| 백엔드/DB | **Supabase** (Postgres + Auth + Storage + Realtime + **RLS**) | 인프라를 안 만듦. 멀티테넌시·권한이 DB에 내장 |
| 프론트 | **Next.js + TypeScript + Tailwind** | 공개페이지 SSR + 내부 SPA 한 코드베이스 |
| 결제 | PG 어댑터 (토스/포트원 등, §06) | 갈아끼우기 가능 |
| 알림 | 알림톡 대행 + SMS (§06) | 현행 인프라 재사용 |
| 잡/자동화 | Supabase Edge Functions / cron | 잔금 독촉·정산 배치 |
| 배포 | Vercel(프론트) + Supabase(백엔드) | 계정 2개로 운영 |

> Supabase 대신 자체 서버도 가능하나, **무팀·고속**에는 관리형이 압도적으로 유리.

## 3.1 멀티테넌시 — tenant_id + RLS
```
모든 테이블에 tenant_id.
Row-Level Security 정책: "사용자는 자기 tenant_id 행만 접근".
→ DB 레벨에서 격리. 애플리케이션 버그가 나도 남의 데이터가 안 샌다.
```
- 이것이 "**본사 DB와 합칠 수도**" (기본: 한 DB에 tenant_id로 공존)
- "**나눌 수도**" (독립 시: 해당 tenant를 **전용 Supabase 프로젝트로 분리 추출**)
- 핵심: 처음부터 tenant_id 경계를 깨끗이 → 나중에 뽑아내기 쉬움

## 3.2 기능 권한 (Entitlement) — 요구 1
```
Plan (요금제)         : 어떤 기능 묶음
TenantEntitlement    : 테넌트별 기능 on/off (요금제 + 개별 조정)
  featureKey: 'contracts' | 'payment_link' | 'kakao' | 'expense'
            | 'fair' | 'microsite' | 'chat' | 'stats' | ...
게이팅: 서버(API)에서 먼저 막고, 화면(메뉴)에서 숨김
```
- 현행 UFFICE의 메뉴가 그대로 **feature key 목록의 초안** (계약/시공/일정/결제/경비/박람회/통계/문자…)
- 업체마다 "이 기능 줄까 말까"를 대시보드에서 토글

## 3.3 구독 — 요구 2
- Plan(무료/기본/프로 등) → 포함 기능 + 한도(계정 수·건수·문자량)
- 구독 상태(활성/연체/해지) → 접근 제어
- 과금: 결제 인프라 재사용 (정기결제/빌링). 초기엔 **수기 개설 + 월청구**로 시작해도 됨

# 4. 데이터 격리 — 합침 / 나눔 (요구 3)

| 모드 | 방식 | 언제 |
|---|---|---|
| **공유(기본)** | 한 DB + tenant_id + RLS | 대부분의 협력업체 |
| **전용(독립)** | 별도 Supabase 프로젝트로 데이터 이전 | 별도 사업자로 독립, 규모 큰 업체 |

- 설계 원칙: **공유로 시작하되 항상 추출 가능하게.** tenant_id 경계와 외래키를 깨끗이 유지하면
  "이 테넌트 데이터만 덤프 → 새 프로젝트로 복원"이 스크립트로 가능.
- 독립은 **프리미엄 옵션**으로 과금 가능.

# 5. 마이그레이션 (요구 4)

직접 DB 접근이 안 되므로:
```
현행(MSSQL 추정) → 당신이 Export (테이블별 CSV/Excel)
                 → 나에게 전달
                 → 내가 Import 스크립트로 신규 스키마에 적재 + 검증
```
- 오히려 직접연결보다 **깔끔**하다 (읽기전용, 사고 위험 없음).
- 이관 순서·원장변환은 [05 마이그레이션 전략] 그대로.
- ⚠️ 이관 데이터에 **개인정보 22,000건**. Export 파일 취급 주의(암호화 전달).

# 6. 속도 전략 — MVP 먼저, 플랫폼은 나중 ★★

"모든 기능 + 멀티테넌트 + 구독 + 마켓"을 한 번에 만들면 오픈이 늦어진다.
**가장 빠른 길 = 나노마스터 한 테넌트로 핵심만 먼저 띄우고, 검증되면 확장.**
단, tenant_id는 **처음부터** 넣는다 (나중에 못 끼움).

## 단계
| 단계 | 범위 | 목표 |
|---|---|---|
| **M0 기반** | Supabase+Next.js 뼈대, 인증, tenant_id, 스키마, 화면 1개 end-to-end | "돌아간다" 확인 |
| **M1 계약 코어** | 계약·계약자·시공·**원장(금액)**·수납 + 나노마스터 데이터 이관 | 실제 업무 대체 시작 |
| **M2 회수·소통** | 결제링크(PG)·알림톡·**잔금 회수 자동화**·일정이력 | 현금흐름 개선(최대 가치) |
| **M3 멀티테넌트** | Entitlement·요금제·구독·2번째 협력업체 온보딩 | 플랫폼화 |
| **M4 대외** | 마이크로사이트·단가공개·채팅·고객포털 | 고객 접점 |
| **M5 경영** | 경비 결재·박람회 손익·정산·BI | 관리 완성 |

> M1~M2까지가 **"현행을 대체하고 돈을 더 걷는"** 실질 가치.
> M3부터가 "남에게 파는" 플랫폼. 순서를 지키면 빠르게 쓰면서 키운다.

# 8. 비용 (개략 — 확정 아님, 변동 가능)

## 8.1 고정비 (월)

| Supabase | **$0** (Free) | **$25/mo** (Pro) | 8GB DB, 100GB 저장, 일일백업. 개발은 무료로 충분 |
| Vercel(프론트) | $0 (Hobby) | $0~$20/mo | 트래픽 늘면 Pro |

| **합계(고정)** | ~$0 | **약 $25~45/mo (₩4~6만)** | 인프라는 저렴 |

## 8.2 사용량 과금 (쓴 만큼)
| 항목 | 단가(개략) | 성격 |
|---|---|---|
| PG 카드수수료 | 결제액의 **약 2.2~3.5%** | 실제 결제 발생 시만. 매출에서 상쇄 |
| 알림톡 | 건당 **약 ₩8~15** (대행사) | 발송량 비례 |
| SMS/LMS 대체 | 건당 **약 ₩20~50** | 알림톡 실패 시 |
| Storage 초과 | GB당 **약 $0.021/mo** | ★ **녹음파일이 변수** |
| 대역폭(egress) | GB당 소액 | 파일 다운로드 많으면 |

## 8.3 ★ 녹음파일 저장 비용 감각
- 통화 5분 ≈ 2~5MB (압축). 월 1,000건 × 3MB ≈ **3GB/월 ≈ 36GB/년**.
- Pro 기본 100GB 안에서 한동안 커버, 이후 GB당 월 $0.02 수준 → **관리 가능하나 누적**.
- 대안: 대용량은 저가 오브젝트 스토리지(R2 등)로 분리 저장 가능.
- ⚠️ 통화녹음은 **녹취 동의 등 법적 고려** 필요 (기능과 별개로 운영정책).

> 요약: **인프라 고정비는 월 4~6만원 수준**. 진짜 비용은 PG수수료·알림톡(둘 다 매출·활동에 비례)과
> 녹음파일이 쌓이는 저장비다. 초기 부담은 매우 작다.

# 9. 단계적 개발 = 버전관리 (덮어쓰기 아님) ★

질문: "코드를 파일 덮어쓰기처럼 바꾸나?" → **아니다. 버전관리(Git)로 한다.**

## 9.1 코드 변경
- 모든 변경은 **Git**으로 추적. 매 변경 = 라벨 붙은 스냅샷.
- 문서 "버전 기록"처럼: 언제 뭘 바꿨는지 다 남고, **언제든 이전으로 되돌림**.
- 파일이 수정·교체돼도 **과거 버전이 사라지지 않는다**. 잘못되면 롤백.
- 기능 추가 = 보통 파일 일부 수정 + 새 파일 추가. 통째 덮어쓰기는 드물다.

## 9.2 ★ 코드 ≠ 데이터 (가장 중요)
```
코드를 아무리 바꿔도 DB의 데이터는 건드리지 않는다.
데이터는 Supabase(DB)에 따로 산다. 화면·로직만 바뀐다.
```
- "덮어쓰면 데이터 날아가나?" → **아니다.** 코드 배포와 데이터는 분리.
- 스키마(테이블 구조)를 바꿀 땐 **마이그레이션**(버전된 변경)으로:
  - 컬럼 추가 등 **기존 데이터 보존**하며 변경.
  - 마이그레이션도 순번·롤백 관리.
- → 단계적 개발 내내 **데이터는 계속 쌓이고 안전**.

# 10. 데이터 보존 원칙 — 전부 남긴다 (분석용) ★★

요구: 상담내역·녹음·작성시각·일정확정시각·경비… **모든 데이터가 남아 향후 예측에 쓰여야 한다.**
→ 이건 이미 이 설계의 **핵심 철학**이다 ([05 P1 원장], [06 이력]). 확장 정리:

## 10.1 삭제하지 않는다 (Append-only / Soft-delete)
- 하드 삭제 없음. "삭제"는 **감춤 플래그**(누가·언제 지웠는지도 기록).
- 모든 변경 = **감사로그**에 시각과 함께 적재.

## 10.2 시각(timestamp)을 다 남긴다
| 데이터 | 남기는 시각 |
|---|---|
| 상담내역 | 작성시각·수정이력, **녹음파일 첨부** |
| 시공예정일 | 확정시각·재조정 이력 (§06) |
| 금액 | 계약·할인·입금·환불·매출취소 각 발생시각 (원장) |
| 상태변화 | 계약/시공/경비 상태 전이 시각 |
| 경비 | 지출일·결재 각 단계 시각 |

## 10.3 상담 + 녹음
```
Consultation (상담)
  contractId?/customerId
  createdAt, editedHistory[]
  body(내용)
  Attachment[] : 녹음파일(audio) · 사진 · 문서
  channel: 전화 | 방문 | 채팅
```
- 현행 상담관리(`/_project/board/1017`)를 계승 + 녹음 업로드 추가.

## 10.4 경비 → 사업 분석
현행 박람회별통계(§04-0.2)의 마진 계산을 **정확한 단일 원장** 위에서 재구현:
```
현장별 마진   = Σ입금(해당 현장) − Σ시공비 − Σ박람회비 − Σ인건비 − Σ경비
월별 마진     = 위를 월 버킷으로 집계
박람회별 손익 = 매출·입금·잔금·비용을 박람회 단위로
영업자별 실적 = 계약·취소·인건비·경비
```
- 경비(Expense)에 **현장/박람회/월** 차원을 태깅 → 매출 원장과 조인 → 손익 자동.
- 현행은 화면마다 계산이 하드코딩돼 숫자가 어긋났으나, **단일 소스**라 항상 일치.

## 10.5 예측(포워드룩킹)
- 모든 게 **시계열 이벤트**로 남으므로:
  - 계약·취소·회수 **추세**, 계절성(입주 성수기)
  - 박람회 투자 대비 수익 → **참가 의사결정 지원**
  - 잔금 회수 예측 → 현금흐름 전망
- 초기엔 추세·이동평균 수준, 데이터 쌓이면 정교화. **데이터를 안 버리는 게 전제** — 이미 충족.
