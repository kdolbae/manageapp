# 0. 전체 그림 — 등록 경로가 2개다

## 경로 A. PC (분리형, 3단계 수기)
```
① /sub/07/?act=write      계약자 등록      → CustomerSeq
② /sub/01/?act=write      계약 등록        → ContractSeq   (①을 검색해서만 선택 가능)
③ /sub/02/?act=sigongwrite 시공 등록       → SigongIdx     (②의 탭에서 진입)
④ /sub/02/ 시공관리 하단   입금 등록        → ChargingSEQ
```
- **각 단계가 완전히 독립된 페이지**. 사람이 4번 이동하며 저장.
- ②의 고객명 필드는 `readonly` — 반드시 ①이 먼저 존재해야 함.

## 경로 B. 태블릿 (통합형, 1화면 1버튼) ★
```
/tablet/01/?act=write   ← 한 페이지에 폼 4개가 나란히 존재
  ├ #con_form      계약자   → POST /sub/07/  (act=writeproc)
  ├ #contactfrm    계약     → POST /sub/01/  (act=writeproc)
  ├ #sigongfrm     시공     → POST /sub/02/  (act=sigongwriteproc)
  └ #chargingFrm   수납     → AJAX /ajax/ajax_liti_bill.asp (act=bill_sub_write)
                              + POST /files/reciept_upload.asp (영수증)
```
> **경로 A와 B는 같은 서버 처리기(`writeproc`)를 재사용**한다. 태블릿은 UI만 다르고
> 뒤에서는 PC와 똑같은 4단계를 순차 실행할 뿐이다.

# 1. 태블릿 통합 등록의 체이닝 메커니즘 ★★

가장 중요한 구조. **숨은 iframe + 서버가 내려주는 콜백 JS** 로 4단계를 이어붙인다.

```html
<iframe name="hiddenfrm" style="display:none;"></iframe>
```

## 1.1 실행 순서

```
[확인] 버튼 → fnSubmit()
   │
   ├─ customerReg()      계약자 유효성 검사
   │     └─ contractReg()      계약 유효성 검사
   │           └─ sigongReg()       시공 유효성 검사 + items 직렬화
   │                 └─ bill_pay_reg()   수납 유효성 검사 → submitYN = true
   │
   └─ if(submitYN):
        #con_form.action = '/sub/07/Default.asp'
        #con_form.target = 'hiddenfrm'
        #con_form [act] = 'writeproc'
        #con_form.submit()
              ↓ (서버가 iframe에 <script>parent.setCustomerSeq(NNN)</script> 응답)
        setCustomerSeq(seq)
              #contactfrm [customer] = seq
              #contactfrm [cusName/cusTEL/cusHP] ← con_form 값 복사
              #contactfrm.action = '/sub/01/Default.asp', act='writeproc'
              #contactfrm.submit()
              ↓ setContractSeq(seq)
        setContractSeq(seq)
              #sigongfrm [SEQ] = seq
              #chargingFrm [ContractSeq] = seq
              #sigongfrm [tabletYN] = 'Y'          ← 태블릿 경유 표시
              #sigongfrm.action = '/sub/02/Default.asp', act='sigongwriteproc'
              접수형태가 '옵션' 이면 ChargingGubun='중도금', 아니면 '계약금'
              #sigongfrm.submit()
              ↓ setSigongIdx(idx)
        setSigongIdx(idx)
              #chargingFrm [SigongIdx] = idx
              #chargingFrm [act] = 'bill_sub_write'
              AJAX POST /ajax/ajax_liti_bill.asp  → 응답 = ChargingSEQ
              #chargingFrm [SEQ] = 응답
              #chargingFrm.submit()   → /files/reciept_upload.asp (영수증 파일)
              ↓ tablet_done()
        tablet_done()
              alert('저장되었습니다.')
              location.replace('/tablet/01/?act=done&contractseq=..&sigongidx=..')
```

## 1.2 검증 함수 체인 (유효성 → 저장이 분리돼 있지 않음)

`customerReg()` 는 마지막 줄에서 `contractReg()` 를 호출하고,
`contractReg()` 는 `sigongReg()` 를, `sigongReg()` 는 `bill_pay_reg()` 를 호출한다.
즉 **검증 함수가 다음 검증 함수를 직접 부르는 재귀적 연쇄**.
어느 한 단계라도 `return` 되면 `submitYN` 이 `true` 가 되지 않아 전체가 중단된다.

## 1.3 이 설계의 위험 ★

| # | 심각도 | 내용 |
|---|---|---|
| E1 | **매우 높음** | **원자성(트랜잭션) 없음.** 4개 저장이 각각 독립 요청. 2단계(계약)에서 실패하면 **계약자만 등록된 고아 레코드**가 남고, 3단계에서 실패하면 계약자+계약만 남는다. 롤백 없음 |
| E2 | 높음 | 서버가 iframe에 `parent.setXxx()` 를 내려주는 방식이라 **에러 응답 시 아무 콜백도 호출되지 않고 조용히 멈춤**. 사용자는 버튼이 사라진 화면만 본다 (`.btn_submit` 을 `visibility:hidden` 처리했으므로 재시도도 불가) |
| E3 | 높음 | 재시도 시 계약자가 중복 생성됨 (실제로 목록에 동일 이름·번호 계약자가 연속 2건 존재하는 사례 확인) |
| E4 | 중간 | `submitYN` 이 전역 변수. `fnSubmit()` 끝에서 `false` 로 되돌리지만 비동기 체인 도중이라 타이밍 의존 |
| E5 | 중간 | 영수증 업로드가 **입금 저장 후 별도 요청** — 업로드 실패해도 입금은 이미 저장됨 |

# 2. 계약자 (Customer)

## 4.3 계약시공 선택 — 타일 UI ★

PC는 `<select>` 드롭다운, **태블릿은 3열 타일 그리드**. 데이터는 동일.

```html
<div onclick="add_itembox(this)"
     data-item="샤워부스1,욕실거울1,세면기1,양변기1"
     data-type=""
     data-free="수전2개(...),수건걸이,..."
     data-price="0"        ← 주방 시공비
     data-priceb="50000"   ← 욕실 시공비
     data-idx="273"        ← 상품 마스터 PK
     class="idx273" id="box0">
```

동작:
```js
add_itembox(obj)    // 이미 .active면 무시 → 같은 상품 중복 선택 불가
  → '상세품목 [{type} 타입] : {item} ※무료시공내역 : {free}' 문자열 생성
  → .items_displaybox 에 <li> 추가 (item_nm / price_k / price_b hidden 포함)
  → obj.addClass('active')
  → caltotal()

remove_itembox(obj) // confirm → .idx{N} 에서 active 제거 → caltotal() → li 삭제

caltotal()          // .tilearea .active 를 전부 순회해 재합산 (누산 아님)
  → #sumcost_k, #gisa_kitchen_pay = Σ data-price
  → #sumcost_b, #gisa_bath_pay    = Σ data-priceb
```

> PC의 `caltotal()` 은 **차감식**(합계에서 빼기), 태블릿은 **전체 재계산**.
> 태블릿 방식이 정확하고, PC 방식은 오차 누적 가능. 같은 이름 함수의 구현이 다름 ★

## 6.1 표시번호는 저장된 ID가 아니다 ★

| 화면 | 첫 행 표시번호 | 실제 PK |
|---|---|---|
| PC 계약목록 | 22323 | ContractSeq 22022 |
| 태블릿 목록 | 22355 | ContractSeq 22022 (동일 건) |
| 계약자 목록 | 21604 | CustomerSeq 21925 |

→ 같은 레코드가 화면마다 **다른 번호**로 보인다.
표시번호 = `전체건수 - 행순번 + 1` 형태의 **계산된 순번**이며, 저장된 식별자가 아니다.
목록 총건수가 다른 이유는 두 화면의 필터 조건이 다르기 때문(PC 893p×25 vs 태블릿 895p×25).

> **업무상 위험**: 직원이 "22323번 건" 이라고 말할 때 PC/태블릿에서 서로 다른 건을 가리킬 수 있고,
> 신규 등록이 발생하면 **같은 건의 번호가 계속 밀린다.**
