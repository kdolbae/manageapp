# 1. 매출취소 — 위치 확정 ★

## 1.2 결론: 태블릿 계약완료 화면에 있다

**`/tablet/01/Default.asp?act=done&ContractSeq={seq}&SigongIdx={idx}`** 하단.
PC 화면(`/sub/`)에는 **매출취소 등록 경로가 존재하지 않는다.**

```html
<h3 class="mTitle3">매출취소내역</h3>
<table> 취소일 · 금액 · 비고 </table>
<a href="javascript:bill_pay_write()" id="btn-bill-reg">＋ 매출취소등록</a>
```

### 전용 엔드포인트 (기존 입금과 완전히 분리됨) ★
```
POST /ajax/ajax_salesCancellation.asp
  act=bill_list       &ContractSeq=       → 계약금액/매출취소총액/실계약금액 요약
  act=bill_sub_list   &ContractSeq=&SigongIdx=  → 매출취소 내역 목록
  act=bill_sub_write  + ChargingDate, Amt, Memos, SigongIdx, ContractSeq
  act=bill_sub_edit   + SEQ
```
입금은 `ajax_liti_bill.asp`, 매출취소는 `ajax_salesCancellation.asp` — **테이블이 다르다.**

### 입력 필드 (입금 폼과 다름)
| name | 라벨 | 비고 |
|---|---|---|
| `ChargingDate` | **취소일** ● | (폼 title 속성은 "입금일" 그대로 — 복사 흔적) |
| `Amt` | **금액** ● | |
| `Memos` | 비고 | |
| `SigongIdx` | | JS가 하드코딩 주입 (`$('#SigongIdx').val('22889')`) |

결제방법·승인번호·카드명·영수증이 **없다** → 매출취소는 순수 회계 조정 레코드.

### 잔존 버그
`bill_sub_del()` 만 여전히 **`ajax_liti_bill.asp`(입금 삭제)** 를 호출한다 ★
```js
url: "/ajax/ajax_liti_bill.asp",
data: "act=bill_sub_del&SEQ="+ SEQ,
```
→ 매출취소 행의 삭제 버튼이 **입금 테이블의 같은 SEQ를 지울 위험**. 확인 필요.

## 1.1 안내문이 잘못됐다
결제내역(`/sub/35/`) 화면 안내문:
> *"…계약관리 > 계약서선택 > 시공관리 > 하단 '상세시공' 리스트 클릭 > view 페이지 하단 '매출취소등록'…"*

`/sub/02/Default.asp?seq=22020` (시공관리) 전체 소스 확인 결과:
- **'매출취소등록' 버튼·링크·함수가 없음**
- 입금 폼의 `ChargingGubun` 은 `계약금`/`중도금`/`잔금`/`환불금액` 4개뿐

→ **안내문의 경로 설명이 실제와 다르다.** 직원이 이 안내를 그대로 따라가면
   PC 화면을 아무리 뒤져도 버튼을 찾을 수 없다. 이것이 §1.3 우회 처리의 원인으로 보인다.

## 1.3 현장 운용 실태 (사용자 확인)
> "우선 입금 수정을 환불로 해서 매출 취소 건을 추가 등록함"

즉 실무에서는 **입금 레코드를 `환불금액`으로 수정**하는 방식으로 처리하고 있다.
(정규 경로는 §1.2 — 태블릿 계약완료 화면)

### 이게 만들어내는 문제
| 구분 | 회계상 의미 | 시스템 반영 |
|---|---|---|
| **환불금액** | 이미 받은 돈을 돌려줌 | `입금액` 에서 차감, `환불금액` 집계에 반영 |
| **매출취소** | 매출 자체를 무효화 | `매출취소총액` 에 반영, `실계약금액` 감소 |

두 값은 §00 §4의 집계식에서 **서로 다른 항목**이다:
```
실계약금 = 시공금액 − 할인 − 상품권       (매출취소가 반영되어야 할 자리)
남은금액 = 실계약금 − 입금 + 환불          (환불이 반영되는 자리)
```
따라서 매출취소를 환불로 대체 입력하면:
- `매출취소총액` 이 계속 0으로 남아 **취소된 매출이 매출로 잡힌 채 유지**
- `환불금액` 이 실제보다 부풀려짐
- 결제내역 상단 "기간 총 결제금액", 통계 화면의 매출 수치가 모두 어긋남

> 계약관리 메인 상단 집계에 `매출취소총액(공급가) 1,664,844,550원` 이 표시되는 것으로 보아
> **과거에는 매출취소가 정상 등록됐던 경로가 있었다.** 지금 그 경로를 못 찾고 있는 상태로 보인다.

## 1.4 확인 필요 (최우선)
`/sub/02/Default.asp?act=sigongview&idx={시공idx}&seq={계약seq}` 소스.
시공관리 하단 '상세시공' 표의 **번호/지점/구분 칸 링크**를 클릭하면 나오는 화면이다.
여기에 '매출취소등록'이 있는지 확인되면 운용 문제가 바로 해소된다.

# 2. 시공관리 재확인 (seq=22020 사례)

첫 회차(seq=22022)와 **페이지 구조는 완전히 동일**. 새로 확인된 데이터 특성만 기록한다.

## 2.1 계약시공에 상품 2개가 이어붙는 형태

표시 문자열:
```
샤워부스유리양면1,욕실거울2,세면기2,양변기2,싱크대상판(아일랜드식탁 포함)
※무료시공내역  수전5개(...),수건걸이,...,현관거울
,    [현관도어락,방문손잡이,집내스위치,공용욕실안쪽문 하단문, 싱크볼 하부장 외부문짝]
```
→ [02 §4.3](02_등록플로우_계약자_계약_시공.md) 의 상품 마스터 기준으로
**idx 135(욕실2+주방1) + idx 150(박테론 항균 5종)** 2건을 선택한 결과.

- 저장은 `|@|` 구분자로 join 되지만, **표시할 때는 구분자가 `, ` 로 치환**되어
  원래 몇 개 상품이었는지 화면에서 구분할 수 없다 ★
- 상품 경계가 사라져 "박테론 5종"이 앞 상품의 무료시공내역처럼 읽힌다

## 2.2 금액 사례 (계산식 검증)
| 항목 | 값 |
|---|---|
| 시공금액 | 720,000 |
| 할인금액 | 220,000 |
| 상품권 | 0 |
| 계약금액 | 500,000 |
| 매출취소총액 | 0 |
| 실계약금 | 500,000 |
| 입금 | 50,000 |
| 환불 | 0 |
| 남은금액 | 450,000 |

→ `계약금액 = 720,000 − 220,000 − 0 = 500,000` ✔ ([01 §1.3](01_페이지별_상세.md) 공식 확인)
→ `남은금액 = 500,000 − 50,000 = 450,000` ✔

## 2.3 상태 불일치 사례
- 시공상태 `예정`
- 시공예정일 주방/욕실 **모두 2026-08-17 입력됨**
- 그런데 **시공담당(기사)이 주방·욕실 둘 다 비어 있음**

→ `예정`(날짜만 잡힘)과 `배정`(기사까지 정해짐)이 구분되는 상태값임이 실데이터로 확인됨.
   [00 §5](00_구조_개요.md) 시공상태 목록의 의미가 명확해졌다.

## 2.4 계약담당과 지점의 관계
- 계약담당: `이찬영`
- 지점: `본사`
- 접수형태: `음성계약`

계약 등록 폼에는 지점 필드가 없고([02 §3.1](02_등록플로우_계약자_계약_시공.md)),
지점은 시공 레코드에 붙는다. 계약담당(사용자)의 소속으로 자동 결정되는 것으로 보이나 미확정.

# 3. 아파트 관리 — 목록 (`/sub/13/`)

## 3.1 검색
| name | 용도 |
|---|---|
| `agency` | 지점 선택 |
| `search` | 아파트명 |
| `keyword` | **박람회명** |

`liti_part_reg()` 가 URL을 직접 조립해 이동 (폼 submit 아님):
```
./?act=list&search={}&agency={}&keyword={}
```

## 3.2 목록 컬럼
번호 · 지점 · 아파트(`시도 / 시군구 / 아파트명`) · 박람회 · 관리

| 항목 | 값 |
|---|---|
| 규모 | 70페이지 × 15건 ≈ **1,050건** |
| 표시번호 vs PK | 1041 ↔ `seq=1350` — **또 계산된 순번** ([02 §6.1](02_등록플로우_계약자_계약_시공.md) 패턴 반복) |
| 수정 | `?act=edit&seq={seq}&search=&field=&page=1` |
| 삭제 | `?act=delete&seq={seq}` — **GET + confirm** |

## 3.3 아파트가 지점에 귀속된다 ★
목록에서 같은 성격의 단지가 지점별로 나뉘어 있다:
- 은평 자이더스타 → 본사
- 힐스테이트메디알레 → 호텔감성
- 첨단풍경채어바니티 → 호텔감성
- 서사 우미린 더 시그니처 → 대구

**아파트 마스터에 `agency` 컬럼이 있고, 중복 검사도 지점을 포함**한다(§3.5).
→ 같은 아파트를 여러 지점이 시공하면 **레코드를 각각 만들어야 하고**,
   통계·검색에서 동일 단지가 분리 집계될 수 있다.

## 3.4 박람회 연결
- 아파트 1건에 박람회명 1개가 연결됨 (예: `첨단3지구 제일풍경채 그랑포레 & 첨단풍경채어바니티`)
- 박람회명 하나가 **여러 아파트에 공유**됨 (위 예시가 2개 아파트에 동일하게 붙음)
- 목록의 박람회 칸이 빈 아파트도 다수 → 선택 항목

## 3.5 등록 폼 (`?act=write`, `act=writeproc`)

| name | 라벨 | 비고 |
|---|---|---|
| `agency` | 지점 | select |
| `area1` / `area2` | 지역코드 | `/js/post_area.js?ver=1` |
| `COURT` | 아파트명 | 실제 필수 (JS 검증) |
| `fairlist` / `fairlistname` | 박람회 | 검색 위젯, readonly |

- **지역 검증이 주석 처리**되어 있어 `COURT`(아파트명)만 있으면 등록 가능
  ```js
  // if( $('#area1').val()=='' ){alert('지역을 선택해 주세요.');...}
  // if( $('#area2').val()=='' ){...}
  if( $('#COURT').val()=='' ){alert('아파트명을 입력해 주세요.');...}
  ```
  → **지역 없는 아파트가 등록될 수 있다.** ([01 §3.2](01_페이지별_상세.md) 에서
    시공완료/후기 목록의 아파트명이 `시도/시군구/단지명` 으로 나오는데, 지역이 비면 `//단지명` 이 됨)

## 3.6 중복 검사 — 응답값이 역직관적 ★

```
POST /ajax/ajax_chk_apt.asp
  COURT, area1, area2, agency, seq
```

```js
success: function(data){
    if( data=='not' ){
        $('#cautionTxt').show();   // "이미 등록되어있습니다" 경고 표시
    }else{
        $('#cautionTxt').hide();
    }
}
```

응답 `'not'` 이 **"중복 있음"** 을 의미한다. 이름과 동작이 반대라 유지보수 시 오독하기 쉽다.

- 4개 필드(`agency`,`area1`,`area2`,`COURT`)가 **모두 채워졌을 때만** 검사가 돈다
  → 지역을 비우고 등록하면 **중복 검사 자체를 건너뛴다**
- `part_proc()` 이 경고 표시 여부(`#cautionTxt` display)로 저장을 막으므로,
  검사를 건너뛴 경우 중복 저장이 그대로 통과

## 3.7 박람회 검색
```
POST /ajax/ajax_fairname_list.asp   ← 신규
  keyword
→ get_fair_info(obj)  : data-name, data-seq
```
- `/ajax/ajax_fair_list3.asp` 를 쓰는 **두 번째 박람회 검색 코드가 같은 페이지에 공존**
  (`#fairname`, `#site_keyword_c`, `get_site_info_c()`, `reset_fair()`)
  → 대응 HTML이 없는 **죽은 코드**. `#area1b`/`#area2b` 도 존재하지 않아 `undefined` 전송

## 3.8 세종시 처리가 화면마다 다르다 ★

| 화면 | `세종특별자치시` 선택 시 |
|---|---|
| PC 계약등록 ([02 §3.3](02_등록플로우_계약자_계약_시공.md)) | 시군구 option의 `value=""` 로 비움 |
| 아파트 등록 (여기) | `"선택"` 기본 option 자체를 제거 |
| 태블릿 통합폼 | 예외 없음 |

같은 `post_area.js` 를 쓰면서 **세 화면이 세 가지로 동작**한다.
세종시 아파트의 `area2` 값이 등록 경로에 따라 달라져 검색·중복검사가 어긋난다.

# 5. 이번 회차 문제점

| # | 심각도 | 위치 | 내용 |
|---|---|---|---|
| G1 | **매우 높음** | 매출취소 | 등록 UI를 찾지 못해 **입금을 환불로 대체 입력** 중. `매출취소총액`이 0으로 남아 매출·환불 집계가 동시에 왜곡됨 |
| G2 | 높음 | 아파트 등록 | 지역 필수 검증이 주석 처리 → **지역 없는 아파트 등록 가능**, 게다가 그 경우 중복 검사도 건너뜀 |
| G3 | 중간 | 아파트 | 아파트가 **지점에 귀속** → 동일 단지가 지점 수만큼 중복 생성, 통계 분산 |
| G4 | 중간 | 세종시 | 지역 처리가 3개 화면에서 **3가지로 다름** |
| G5 | 중간 | 시공 표시 | 계약시공 상품 여러 건이 `, ` 로 이어붙어 **경계가 사라짐** |
| G6 | 중간 | `ajax_chk_apt` | 응답 `'not'` 이 "중복 있음"을 의미 — 이름과 동작이 반대 |
| G7 | 낮음 | 아파트 목록 | `<td class=mBox align=center>` 미닫음 (ASP 조립 오류) |
| G8 | 낮음 | 아파트 등록 | 박람회 검색 코드 2벌 공존, 한쪽은 죽은 코드(`#area1b` 미존재 → undefined 전송) |
| G9 | 낮음 | 아파트 | 삭제가 GET 링크 |
| G10 | 낮음 | 아파트 목록 | 검색 select에 선택값 유지 로직 없음 (전 시스템 공통 패턴) |
