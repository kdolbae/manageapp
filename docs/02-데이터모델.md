# 데이터 모델 / 스키마 설계

- 문서 버전: v0.1
- 대응 파일: [`prisma/schema.prisma`](../prisma/schema.prisma)

3계층(메달리온) 구조로 **원본 보존(Bronze) → 표준화(Silver) → 자산화(Gold)**를 분리한다.

## 1. Bronze — 스테이징 (`stg` 스키마)

UPIS 실제 스키마를 아직 확보하지 못했으므로, **스키마 무관 방식**으로 원본을 손실 없이 적재한다.
스키마가 확정되면 여기서 표준 모델로 매핑한다.

```
StgBatch (이관 배치)
  ├─ id, sourceSystem="UPIS", sourceObject, status, rowCount, startedAt, finishedAt
  └─ records → StgRecord[]

StgRecord (원본 1행)
  ├─ batchId → StgBatch
  ├─ sourceObject      원본 테이블명
  ├─ sourcePk          원본 PK(문자열)
  ├─ payload (JSONB)   원본 1행 전체
  └─ ingestedAt
```

- **왜 JSONB인가**: UPIS 컬럼 구조를 모르는 상태에서도 즉시 적재를 시작할 수 있고,
  이관 재실행·감사·대사(reconciliation)의 원천이 된다.
- 스키마 확보 후에는 `sourceObject`별 전용 스테이징 테이블로 구체화할 수 있다.

## 2. Silver — 표준 계약 도메인 (`core` 스키마)

```
Party (거래처/당사자) 1──* PartyContact (담당자)
  │
  │ counterparty
  ▼
Contract (계약) ─┬─* ContractItem      (품목/조건)
  │ parent/revisions ├─* ContractDocument  (문서/첨부)
  │ (변경·부속계약)    ├─* ContractEvent     (생애주기 이벤트)
  │                  └─* Settlement       (청구/수납/지급)
  ▼
User (내부 사용자)
```

### 핵심 설계 포인트

- **provenance(출처) 필드**: `Party`, `Contract`에 `sourceSystem`/`sourcePk`/`ingestedAt`을 두어
  각 표준 레코드가 UPIS 원본 어디서 왔는지 추적한다. → 데이터 자산화의 계보 기반.
  `@@unique([sourceSystem, sourcePk])`로 **재이관 시 멱등(중복 방지)**을 보장한다.
- **계약 개정 체인**: `Contract.parent/revisions` 자기참조로 변경·부속계약을 원계약에 연결.
- **상태 머신**: `ContractStatus` = DRAFT → REVIEW → SIGNED → ACTIVE → (RENEWED | EXPIRED | TERMINATED).
- **금액 정밀도**: 금액은 `Decimal(18,2)`, 수량은 `Decimal(18,4)`로 부동소수 오차 방지.

### 주요 엔터티 요약

| 엔터티 | 역할 | 비고 |
| --- | --- | --- |
| `Party` | 계약 당사자(법인/개인) | `regNo`는 마스킹 대상 |
| `Contract` | 계약 본체 | `code` 유일, 개정 체인 지원 |
| `ContractItem` | 계약 품목/조건 | 금액 = 수량×단가 |
| `ContractEvent` | 체결·갱신·해지 이벤트 로그 | 감사 추적 |
| `Settlement` | 청구/수납/지급 | 연체(OVERDUE) 관리 |
| `User` | 내부 사용자/권한 | 자산 소유자 지정 |

## 3. Gold — 데이터 자산 카탈로그 (`asset` 스키마)

데이터 자산화의 핵심. 각 데이터셋을 **자산**으로 등록하고 메타·계보·품질을 관리한다.

```
DataAsset (데이터 자산)
  ├─ key(유일), name, layer(BRONZE/SILVER/GOLD), sourceSystem, refreshCadence, owner→User
  ├─ fields        → DataAssetField[]  (데이터 사전: name, dataType, isPii, isRequired)
  ├─ lineage       → DataLineage[]     (원본→변환 계보)
  └─ qualityChecks → DataQualityCheck[](완전성/유효성/유일성/정합성/적시성 + 통과율)
```

| 자산 4요소 (기획서 §3) | 매핑 |
| --- | --- |
| 표준 스키마 | `DataAssetField` (데이터 사전) |
| 계보(Lineage) | `DataLineage` + 코어의 provenance 필드 |
| 품질(Quality) | `DataQualityCheck` (dimension별 pass/warn/fail, passRate) |
| 버전/카탈로그 | `DataAsset` (자산 목록·소유자·갱신주기) |

## 4. 스키마 분리 & 마이그레이션

- PostgreSQL의 스키마 3개(`stg`, `core`, `asset`)로 물리적으로 분리 → 권한/보존정책 분리 용이.
- Prisma `multiSchema` 프리뷰 기능 사용.
- 마이그레이션: `npx prisma migrate dev` (DB 확보 후). 초기 마이그레이션 SQL 초안은
  [`prisma/migrations/0001_init/migration.sql`](../prisma/migrations/0001_init/migration.sql) 참고.

## 5. 열린 질문 (UPIS 스키마 확보 시 확정)

1. UPIS의 계약/거래처/정산 테이블명과 PK는? → `StgRecord.sourceObject/sourcePk` 매핑 확정
2. 계약 상태 코드 체계는? → `ContractStatus` 매핑표 작성
3. 첨부파일은 DB(BLOB) vs 파일서버? → `ContractDocument.url` 전략 결정
4. 개인정보 항목/보존기간 정책은? → `isPii` 표시 및 마스킹 규칙
