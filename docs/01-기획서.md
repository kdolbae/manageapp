- 문서 버전: v0.1 (초안)

## 1. 배경

현재 계약 업무는 레거시 시스템 **UPIS**에서 운영되고 있다. 올해 안에 UPIS를 대체하는
신규 서비스를 갖추되, 단순 기능 이관에 그치지 않고 **UPIS DB 전체를 가져와
계약 데이터를 재사용 가능한 데이터 자산으로 전환(데이터 자산화)**하는 것이 핵심 목표다.

### 문제 정의

- UPIS 데이터가 레거시 스키마에 묶여 있어 **재활용·분석·연계가 어렵다.**
- 계약 정보가 표준화되어 있지 않아 **동일 개념이 흩어져 중복·불일치**한다.
- 데이터의 **출처/변경 이력/품질**을 추적할 수 없어 신뢰도가 낮다.

## 2. 목표 (Goals)

1. **완전 이관**: UPIS DB의 모든 데이터를 손실 없이 신규 시스템으로 옮긴다.
2. **데이터 자산화**: 흩어진 계약 데이터를 표준 모델로 정규화하고,
   출처(lineage)·품질·버전을 갖춘 **데이터 자산 카탈로그**로 관리한다.
3. **대체 서비스**: UPIS의 계약관리 기능을 대체하는 운영 서비스를 제공한다.

### 비목표 (Non-Goals) — 이번 단계 제외

- UPIS 화면/UX의 1:1 복제
- 회계/전표 시스템 대체 (연계는 후속 과제)
- 실시간 CDC(변경데이터캡처) — 초기엔 배치 이관으로 시작

## 3. "데이터 자산화"의 정의 (이 프로젝트 기준)

계약 데이터를 **관리 대상 자산**으로 다룬다는 의미이며, 자산이 갖추어야 할 4요소:

| 요소 | 설명 | 구현 위치 |
| --- | --- | --- |
| **표준 스키마** | 동일 개념은 하나의 표준 엔터티로 정의 | Silver 코어 모델 |
| **계보(Lineage)** | 각 데이터가 UPIS 어느 원본에서 왔는지 추적 | `data_lineage` |
| **품질(Quality)** | 필수값·형식·정합성 검증 결과를 기록 | `data_quality_check` |
| **버전/카탈로그** | 데이터셋 정의·소유자·갱신주기를 목록화 | `data_asset`, `data_asset_field` |

## 4. 범위 (Scope)

### 4.1 데이터 도메인 (UPIS에서 넘어올 것으로 가정)

> 실제 UPIS 스키마 확보 시 아래 목록을 확정한다. 현재는 계약관리 시스템의
> 일반적 구성을 기준으로 한 **가정치**다.

- 거래처/당사자 (회사, 담당자)
- 계약 (본계약, 부속/변경계약)
- 계약 항목·조건 (금액, 기간, 갱신조건)
- 계약 대상 품목/서비스
- 대금/정산 (청구, 수납, 지급)
- 계약 문서/첨부
- 계약 이력 (체결·갱신·해지 이벤트)
- 사용자/권한

### 4.2 기능 범위

- 계약 등록·조회·수정·검색
- 계약 상태 관리 (초안 → 검토 → 체결 → 이행 → 갱신/만료/해지)
- 만료·갱신 알림
- 데이터 자산 카탈로그 조회 (데이터셋·계보·품질 대시보드)

## 5. 아키텍처: 3계층(메달리온) 데이터 파이프라인

레거시 스키마를 확보하지 못한 상태에서도 안전하게 시작할 수 있도록,
**원본 보존 → 표준화 → 자산화**의 3계층으로 분리한다.

```
UPIS 원본
   │ 추출(dump/접속/CSV)
   ▼
Bronze  stg_*            원본을 형변환 없이 그대로 적재(감사·재처리 대비)
   │ 정제/표준화(매핑 규칙)
   ▼
Silver  core 엔터티       표준 계약 모델(정규화, 관계 명확)
   │ 집계/카탈로그화
   ▼
Gold    data_asset 등     재사용 가능한 데이터 자산 + 메타/계보/품질
```

- **Bronze**: UPIS를 손실 없이 미러링. 이관 재실행·대사(reconciliation)의 기준.
- **Silver**: 표준 엔터티로 정규화. 실제 서비스가 읽고 쓰는 계층.
- **Gold**: 분석·재사용을 위한 자산 카탈로그와 파생 데이터셋.

## 6. 기술 스택

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 프런트/백엔드 | Next.js(App Router) + TypeScript | 단일 코드베이스, 국내 SaaS에 널리 검증 |
| ORM | Prisma | 스키마 우선 설계·마이그레이션·타입 안전 |
| DB | PostgreSQL | JSONB(원본 적재)·스키마 분리·정합성 |
| 이관 | Node 스크립트(배치) | Prisma와 동일 런타임, 재실행 안전 |

> PostgreSQL 호스팅으로 Supabase를 사용할 수 있으나, **클라우드 리소스 생성은
> 사용자 승인 후** 진행한다. 이번 단계는 코드/스키마 산출까지만.

## 8. 리스크 & 확인 필요 사항

- **UPIS 스키마 미확보**: 스테이징 매핑은 실제 스키마 확보 후 확정해야 함.
  → 덤프 파일 또는 접속 정보, 혹은 테이블 목록/컬럼 정의 필요.
- **개인정보/민감정보**: 계약 데이터에 개인정보가 포함될 수 있음.
  이관 시 접근통제·마스킹·보존기간 정책 필요.
- **대사 기준**: 이관 성공 판정을 위한 행수·금액 합계 등 검증 기준 합의 필요.
